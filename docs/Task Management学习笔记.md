## 1. 先建立正确直觉

Task Management 要解决的问题不是“怎样在后台跑一段代码”，而是：

> 一项可能耗时、失败、需要重试、需要被用户查询或取消的工作，怎样在请求结束、进程重启或 Worker 异常后，仍然被可靠地管理。

例如，一个用户发起“处理一份文件”的操作。处理可能要经过解析、OCR、清洗、模型调用和保存结果，持续几十秒甚至几分钟。

如果系统只在 HTTP 请求里同步处理，会有几个问题：

- 请求长时间不返回，浏览器、网关或客户端可能超时；
- 用户不知道当前进行到哪里；
- 失败后只能重新发起整个请求，无法区分是否已部分完成；
- 服务进程重启时，运行中的工作可能直接消失；
- 多个 Worker 可能意外执行同一份工作。

Task Management 把这项工作从一次瞬时请求，变成一个有身份、状态、历史和管理能力的持久化对象。

```text
用户发起工作
  -> 创建 Task
  -> 返回 task_id
  -> 后台 Worker 执行
  -> Task 持续记录状态和事件
  -> 用户查询结果、取消或重试
```

Task 的价值不在于“异步”二字，而在于可管理的生命周期。

## 2. 容易混淆的五个概念

### 2.1 HTTP Request

HTTP Request 是一次网络通信。它有开始和结束，通常应尽量短。

它适合：

- 参数校验；
- 创建资源；
- 查询状态；
- 发起取消或重试命令。

它不适合承载长时间、可恢复的业务执行。

### 2.2 进程内异步任务

例如协程、线程池任务或运行时的 `asyncio.Task`，本质上是当前进程中的执行单元。

它们可以解决“不阻塞当前线程或事件循环”的问题，但通常不能天然解决：

- 进程重启后的恢复；
- 多进程或多机器的共享协调；
- 用户查询历史状态；
- 审计、重试与幂等；
- 任务长期持久化。

因此，进程内异步任务可以是 Worker 内部的实现细节，但不等于业务上的 Task。

### 2.3 Platform Task

Platform Task 是面向业务和用户管理的、可持久化的工作单元。

它至少应回答：

- 这是什么任务？
- 谁发起、谁可以查看和操作？
- 它现在是什么状态？
- 已尝试执行几次？
- 最终结果在哪里？
- 失败原因是什么？
- 是否允许取消或重试？

### 2.4 Conversation Turn

Turn 是一次对话中的执行和顺序边界，例如“用户输入 -> 系统生成回复”。

它可能触发一个长任务，但两者不是同一对象：

- Turn 关注同一会话的顺序、上下文和消息事实；
- Task 关注后台工作的生命周期、可恢复执行和运营管理。

一个 Turn 可以创建一个 Task；一个 Task 也可能完全不属于任何对话。

### 2.5 Workflow

Workflow 是多个步骤、多个 Task 或多个条件分支的编排。

```text
Workflow
  -> Task A：下载资料
  -> Task B：解析内容
  -> Task C：人工审核
  -> Task D：发布结果
```

Task 是可执行的原子工作单元；Workflow 是组织多个工作单元的流程。先把单个 Task 的状态、失败、取消和恢复做清楚，才适合讨论 Workflow。

## 3. Task 的完整生命周期

从业务视角看，一个 Task 通常会经历：

```text
创建
  -> 排队等待
  -> 被 Worker 领取
  -> 执行
  -> 成功 / 失败 / 取消
  -> 必要时重试或恢复
```

从用户视角看，Task 应该有清晰的问题答案：

| 用户问题 | 系统应能回答的内容 |
| --- | --- |
| 我的任务创建成功了吗？ | task_id、创建时间、初始状态 |
| 为什么还没开始？ | 正在排队、何时可运行、是否被限流 |
| 正在做什么？ | 当前状态、可选进度、开始时间 |
| 为什么失败？ | 安全的错误码、可读说明、是否可重试 |
| 我能停止它吗？ | 是否可取消、取消是否已经确认 |
| 结果在哪里？ | 结果摘要或结果资源引用 |
| 服务重启后会怎样？ | 任务会被恢复、重试或明确标记失败 |

## 4. 状态机与状态迁移

状态机是 Task Management 的核心。它规定每个状态的业务含义，以及哪些转换是合法的。

### 4.1 一个可学习的最小状态机

```text
QUEUED
  -> RUNNING
  -> SUCCEEDED
  -> FAILED

FAILED
  -> RETRY_WAIT
  -> QUEUED

QUEUED
  -> CANCELLED

RUNNING
  -> CANCEL_REQUESTED
  -> CANCELLED
```

常见状态含义：

| 状态 | 含义 |
| --- | --- |
| `QUEUED` | 已创建，等待可用 Worker 执行。 |
| `RUNNING` | 已被一个 Worker 领取，正在执行。 |
| `SUCCEEDED` | 已成功结束，结果已经可引用。 |
| `FAILED` | 已失败且当前不能继续自动重试。 |
| `RETRY_WAIT` | 本次尝试失败，但等待退避时间后可以再执行。 |
| `CANCEL_REQUESTED` | 已请求停止，执行器尚未确认停止。 |
| `CANCELLED` | 已确认不再执行。 |

### 4.2 为什么“请求取消”不等于“已取消”

排队中的 Task 尚未执行，通常可以直接变成 `CANCELLED`。

运行中的 Task 可能正在调用外部服务、写入文件或处理大数据。此时系统通常无法安全地从外部强行杀死执行线程。

更真实的语义是：

```text
用户点击取消
  -> 系统记录 CANCEL_REQUESTED
  -> 执行器在安全边界检查取消信号
  -> 清理临时资源
  -> 写入 CANCELLED
```

因此，Task Management 需要诚实表达“取消正在处理中”，不能把取消请求伪装成已经停止。

### 4.3 状态机的不变量

设计状态机时，应先写出不可被破坏的规则：

- 一个 Task 在同一时刻最多只能有一个有效执行者；
- 终态 Task 不应被普通执行流程重新领取；
- `SUCCEEDED` 必须有可访问的结果或明确的结果引用；
- 每次执行尝试都应可追溯；
- 取消、重试和恢复必须有明确的合法起点；
- 过期 Worker 不能覆盖新 Worker 的执行结果。

状态名可以变化，但这些不变量不应含糊。

## 5. 一个 Task 应保存哪些事实

Task 数据模型不需要一开始就很复杂，但要区分“任务事实”“执行尝试”“审计事件”和“业务结果”。

### 5.1 Task 本身

Task 通常保存：

```text
身份：id、task_type
归属：owner、创建来源
状态：status、创建/开始/结束时间
输入：可信的输入引用或输入快照
结果：结果资源的引用或摘要
执行：已尝试次数、最大次数、下次可执行时间
协调：当前租约、持有 Worker、租约到期时间
控制：幂等键、取消请求信息
```

### 5.2 Attempt：一次执行尝试

同一个逻辑 Task 可能因瞬时错误执行多次。每一次尝试都应独立记录：

- 第几次尝试；
- 哪个 Worker 执行；
- 开始和结束时间；
- 失败类别和安全错误信息；
- 是否因取消、超时或租约失效结束。

这样用户看到的是一个稳定的 Task，运营和排障人员仍能看到完整的尝试历史。

### 5.3 Event：生命周期审计事实

Event 用来记录状态之外的重要动作，例如：

```text
TASK_CREATED
TASK_CLAIMED
TASK_STARTED
TASK_CANCEL_REQUESTED
TASK_RETRY_SCHEDULED
TASK_SUCCEEDED
TASK_FAILED
TASK_RECOVERED
```

Task 当前状态告诉我们“现在怎样”；Event 告诉我们“它如何走到现在”。

### 5.4 业务结果不等于 Task

Task 的结果通常是一个引用：例如处理后的文件、生成的报告、创建的数据记录或下载地址。

Task 不应该成为所有业务数据的替代品。它负责管理一次执行；业务实体仍然负责保存业务事实。

## 6. 任务从创建到完成的执行链路

一条健康的 Task 链路可以这样理解：

```text
1. 客户端发起业务请求
2. 服务端校验身份、权限、输入和幂等键
3. 服务端在事务中创建 Task 与创建事件
4. 服务端快速返回 task_id
5. Worker 领取可执行 Task
6. Worker 执行业务逻辑
7. Worker 写入成功、失败、取消或重试等待状态
8. 客户端通过查询或推送得到最新状态
```

这里有两个重要边界：

1. **创建 Task 与 HTTP 请求的边界**：请求成功的含义通常是“任务已被可靠登记”，不是“业务处理已完成”。
2. **领取 Task 与执行外部操作的边界**：领取和状态变更应使用短事务；耗时的外部操作不应长期占用数据库事务或连接。

## 7. Worker、队列、领取与租约

### 7.1 Worker 做什么

Worker 是持续寻找并执行待处理 Task 的后台执行者。

它的职责一般包括：

- 发现当前可执行的 Task；
- 安全领取一个 Task；
- 调用对应的业务执行器；
- 写入终态或重试信息；
- 定期处理过期租约；
- 记录日志、指标和审计事件。

Worker 不是业务规则本身。它更像调度和运行外壳；具体业务工作由对应的执行器完成。

### 7.2 为什么要“领取”

假设两个 Worker 同时看到同一条 `QUEUED` Task：

```text
Worker A：我看见它了，我来执行
Worker B：我也看见它了，我也来执行
```

如果没有原子领取，就可能产生双重扣费、重复写入、重复发消息或重复生成文件。

因此，领取必须是一个原子动作：只有一个 Worker 能成功把 Task 从“可执行”变成“我正在执行”。

数据库队列常见做法是行锁加跳过锁定行，例如 PostgreSQL 中的 `FOR UPDATE SKIP LOCKED`。学习它时重点不是记 SQL，而是理解它保证的事实：并发 Worker 不会都拿到同一条工作。

### 7.3 为什么需要租约

只记录 `RUNNING` 还不够。

如果 Worker 在运行中崩溃，Task 会永久停在 `RUNNING`，其他 Worker 不敢接手。租约为执行权设置过期时间：

```text
Worker 领取 Task
  -> 写入 lease_token 和 lease_expires_at
  -> 运行期间定期续租
  -> 崩溃后不再续租
  -> 到期后可被恢复机制处理
```

租约不是“保证永不重复执行”的魔法。网络分区、暂停或超时下，旧 Worker 与新 Worker 仍可能短暂重叠。因此业务执行仍需要幂等设计。

### 7.4 为什么完成时要校验租约

假设 Worker A 停顿太久，租约过期；系统把 Task 交给 Worker B。之后 Worker A 又恢复并试图写入“成功”。

如果系统允许 A 直接覆盖结果，就会出现过期 Worker 污染新执行结果的问题。

因此，完成状态更新通常要同时校验：

```text
task_id 一致
且当前状态仍允许完成
且 lease_token 仍属于当前 Worker
```

## 8. 可靠性四件套：幂等、重试、取消、恢复

### 8.1 幂等：重复请求不能重复做事

用户可能因为网络慢、按钮重复点击、浏览器重试或网关超时，多次发送同一个创建请求。

幂等的目标是：

> 同一个逻辑请求被重复提交，系统得到同一个逻辑结果，而不是重复产生副作用。

常见方式是客户端携带幂等键，服务端按“主体 + 操作类型 + 幂等键”识别重复请求。

需要特别处理：相同幂等键但不同业务输入不能静默复用，应明确报错，因为这通常代表客户端程序错误或用户操作混乱。

### 8.2 重试：不是所有失败都应该重试

先按失败性质分类：

| 失败类型 | 例子 | 一般处理 |
| --- | --- | --- |
| 瞬时失败 | 网络闪断、服务限流、临时超时 | 延迟重试 |
| 永久失败 | 参数非法、权限不足、文件格式不支持 | 直接失败 |
| 不确定失败 | 外部请求超时，但对方可能已执行 | 先查状态或依赖幂等键，再决定是否重试 |

重试还需要：

- 最大尝试次数；
- 指数退避或其他等待策略；
- 随机抖动，避免大量任务同时再次冲击下游；
- 明确记录每次尝试的错误；
- 重试耗尽后的终态。

### 8.3 取消：应是协作式的

取消有三个层次：

```text
取消排队任务：直接阻止开始
取消运行任务：请求执行器在安全点停止
取消外部副作用：可能无法撤销，需要补偿或人工处理
```

例如一个外部系统已经接收请求，即使本地 Task 被取消，也不代表外部世界已经恢复原状。此时需要明确“取消的边界”，必要时使用补偿操作，而不能承诺不真实的完全回滚。

### 8.4 恢复：崩溃后不能遗忘 Task

恢复机制通常关注：

- 长时间未续租的 `RUNNING` Task；
- 进程重启前尚未结束的工作；
- 重试时间已到的 `RETRY_WAIT` Task；
- 已写出部分结果但未写入最终状态的 Task。

恢复不是简单地“重新执行一遍”。需要结合任务类型、已完成步骤、幂等设计和外部副作用判断：重试、标记失败、人工介入，还是继续后续步骤。

## 9. 任务结果、进度、权限与审计

### 9.1 结果

任务成功时，应提供用户真正需要的结果：

- 结果资源引用；
- 下载入口；
- 创建后的业务对象标识；
- 简洁摘要。

不要把执行过程中的全部内部数据、文件路径、堆栈或外部服务原始错误直接给客户端。

### 9.2 进度

不是所有 Task 都能给出准确百分比。应区分：

| 进度形式 | 适用情况 |
| --- | --- |
| 状态型进度 | 排队、运行、重试等待、已完成；大多数任务都适用。 |
| 阶段型进度 | 已下载、已解析、已生成、已保存；适合有稳定步骤的任务。 |
| 百分比进度 | 总工作量可估算，例如固定页数或固定条目数。 |

如果进度不可靠，宁可展示阶段和状态，也不要制造虚假的 87%。

### 9.3 权限

Task 是资源，通常需要明确：

- 谁可以创建；
- 谁可以查看；
- 谁可以取消；
- 谁可以重试；
- 管理员是否拥有额外权限；
- 结果资源是否沿用 Task 的访问边界。

客户端传入的 `owner`、状态或 Task ID 不构成授权依据，服务端必须根据可信身份和资源归属重新判断。

### 9.4 审计

Task 的审计至少应能还原：

- 谁创建任务；
- 何时被哪个 Worker 领取；
- 尝试过多少次；
- 谁请求了取消或重试；
- 最终状态及安全失败原因；
- 结果资源是什么。

## 10. 常见实现方案与适用范围

### 10.1 进程内后台任务

```text
HTTP 请求 -> 协程 / 线程 -> 完成
```

适合：本地开发、极短的非关键辅助工作、进程重启后可丢失的任务。

不足：无法可靠恢复，多实例间无法协调，不适合正式的 Task Management。

### 10.2 数据库持久化队列

```text
数据库任务表 -> Worker 轮询领取 -> 执行 -> 更新状态
```

适合：已有关系型数据库、任务量中等、需要事务一致性、需要审计和可查询生命周期的系统。

优点：少引入一个基础设施，状态、事件与业务数据容易保持一致。

注意：需要做好索引、短事务、领取策略、租约、恢复扫描和数据库容量治理。

### 10.3 消息队列 + Worker

```text
业务服务 -> 消息中间件 -> Worker 集群
```

适合：任务吞吐高、生产者与消费者需解耦、需要削峰、多种消费者或跨系统事件分发。

注意：消息已经被消费不等于业务已经完成。任务状态仍需要持久化；消息队列不能替代 Task 的生命周期模型。

### 10.4 成熟任务框架

例如专用的 Job/Task 框架。

适合：调度、重试、并发控制、分布式 Worker 等需求已经稳定，团队愿意接受框架约束与运维成本。

学习顺序上，应先理解状态机、幂等、租约与失败语义；否则换任何框架都只是把复杂问题藏进配置。

## 11. 测试与观测应该证明什么

### 11.1 最小测试矩阵

| 场景 | 应证明的事实 |
| --- | --- |
| 正常执行 | Task 从排队到成功，结果可访问。 |
| 两个 Worker 并发 | 同一 Task 只会被一个 Worker 有效领取。 |
| 重复创建请求 | 相同幂等键不会创建重复 Task。 |
| 相同幂等键、不同输入 | 系统明确拒绝冲突请求。 |
| 瞬时失败 | 按策略进入重试等待，随后再次执行。 |
| 永久失败 | 不自动重试，失败原因安全可见。 |
| 排队时取消 | Task 不会被执行。 |
| 运行时取消 | 状态先进入取消请求，执行器确认后才取消完成。 |
| Worker 崩溃 | 租约到期后可恢复或明确失败。 |
| 过期 Worker 恢复 | 旧 Worker 不能覆盖新 Worker 的结果。 |
| 权限不足 | 非所有者无法查看、取消或重试。 |

### 11.2 需要观测的指标

至少应关心：

- 队列长度；
- 排队等待时间；
- 执行耗时分布；
- 成功率、失败率、重试率；
- 取消率；
- 租约过期或恢复次数；
- 各类错误码数量；
- Worker 的并发度与空闲情况。

指标不是为了“看起来专业”，而是帮助判断系统慢在哪里、失败是否集中、是否有任务卡死，以及何时需要扩容或限流。

## 12. Task 与 Workflow 的边界

Task Management 解决“一个任务怎样可靠完成”。

Workflow 解决“多个任务怎样按条件、依赖和分支组合”。

不要因为看到多个步骤，就立刻做 Workflow。例如“解析 -> 清洗 -> 保存”可以仍是一个 Task 的内部步骤；只有步骤需要独立排队、独立重试、独立人工审批、独立复用或跨系统协调时，才有必要提升为多个 Task 或 Workflow 节点。

典型升级信号：

- 出现明确的任务依赖图；
- 某个步骤需人工等待或审批；
- 不同步骤由不同团队或不同系统执行；
- 每一步需要独立重试、独立结果和独立权限；
- 需要可视化查看整条业务流程。

## 13. 推荐学习顺序

不要一次性钻进数据库锁、消息队列或框架配置。推荐按下面顺序学习，每一步都写出自己的结论。

### 第一步：概念与边界

学习内容：第 1、2、3 节。

学习目标：能够用自己的话区分 Request、进程内异步任务、Task、Turn 和 Workflow。

练习：任选“文件处理”“生成报告”“批量导入”之一，说明它为什么需要或不需要 Task。

### 第二步：状态机

学习内容：第 4 节。

学习目标：能画出状态图，说明终态、取消、失败和重试的合法转换。

练习：回答“运行中的任务被取消、Worker 同时崩溃时，最终可能处于哪些状态，为什么”。

### 第三步：数据与事实

学习内容：第 5 节。

学习目标：理解 Task、Attempt、Event、业务结果是四类不同的东西。

练习：为一个“导入表格”任务列出应保存的输入、结果、尝试和事件。

### 第四步：执行协调

学习内容：第 6、7 节。

学习目标：理解原子领取、短事务、租约、续租和过期 Worker 保护。

练习：解释两个 Worker 为什么不能只通过“先查询状态再更新”领取任务。

### 第五步：可靠性

学习内容：第 8 节。

学习目标：理解“至少一次执行”以及幂等为什么不可省略。

练习：设计一个网络超时场景：调用方不知道外部操作是否成功时，该怎样避免重复副作用。

### 第六步：产品与运营边界

学习内容：第 9、11 节。

学习目标：能说明用户能看到什么、哪些信息不应暴露、怎样判断系统健康。

练习：为一个失败 Task 写出用户可见提示和内部审计记录分别包含什么。

### 第七步：方案选择与未来边界

学习内容：第 10、12 节。

学习目标：能根据规模、可靠性和运维要求解释为什么选进程内、数据库队列、消息队列或成熟框架。

练习：说明什么信号出现后，才值得从单个 Task Management 系统升级到 Workflow。

## 14. 常见误区

### 误区一：把异步函数当成任务系统

异步只是不阻塞当前执行线程；它不自动提供持久化、恢复、权限、审计和重试。

### 误区二：只有成功和失败两种状态

排队、运行、等待重试、取消请求、租约过期都具有不同的业务含义。状态过少会让错误处理和用户体验变得模糊。

### 误区三：用全局内存锁解决分布式执行

内存锁只在一个进程内有效。多个进程或多台机器时，需要共享的协调事实。

### 误区四：认为队列天然保证“恰好一次”

现实系统更常见的是至少一次执行。网络、崩溃和超时会带来不确定性，幂等必须由业务设计承担。

### 误区五：取消就是立即杀掉执行线程

强制中断可能留下半写入的数据、未关闭的文件和不一致的外部副作用。多数业务任务应协作式取消。

### 误区六：失败后无限重试

无限重试会放大错误、挤占资源、持续冲击外部服务。重试需要分类、上限、退避和人工介入出口。

### 误区七：把所有步骤都做成独立 Task

这会过早引入编排、依赖、监控和事务复杂度。内部不可独立管理的短步骤通常仍属于一个 Task。

### 误区八：先选框架，再定义状态和语义

框架不能替你决定“什么时候可重试”“取消是否生效”“结果如何审计”。这些首先是产品和领域语义。

## 15. 术语速查

| 术语 | 简要解释 |
| --- | --- |
| Task | 一项可持久化管理的后台工作。 |
| Worker | 领取并执行 Task 的后台执行者。 |
| Queue | 等待被执行的 Task 集合或其传递机制。 |
| Claim | Worker 原子地取得一个 Task 的执行权。 |
| Lease | 有过期时间的临时执行权。 |
| Heartbeat | Worker 续租或报告仍存活的动作。 |
| Attempt | 同一 Task 的一次执行尝试。 |
| Idempotency | 重复请求不重复产生业务副作用的性质。 |
| Retry | 失败后按策略再次尝试执行。 |
| Backoff | 重试前的等待策略。 |
| Jitter | 在等待时间中加入随机扰动，防止同时重试。 |
| Cancellation | 对任务提出停止请求及其最终确认过程。 |
| Recovery | 崩溃、租约过期或重启后对未完成 Task 的处置。 |
| Compensation | 外部副作用已发生且无法回滚时，执行补救动作。 |
| Workflow | 多个 Task 或步骤的依赖、分支和编排。 |

## 一句话总结

```text
Task Management 不是“后台运行代码”，
而是把一项业务工作变成可识别、可追踪、可控制、可恢复的生命周期事实。

先定义边界和状态机，
再处理领取和租约，
然后补齐幂等、重试、取消与恢复，
最后才选择队列、框架或 Workflow。
```
