当前专题

Task Management 学习路线

先理解业务语义与可靠性原则，再讨论任何数据库、消息队列或任务框架的技术选型。

先分清对象

Task 不是“后台跑一段代码”

Task 是一项可持久化、可查询、可取消、可重试、可恢复的后台工作。

  • Request：一次网络通信，应尽量短。
  • 进程内异步任务：当前进程的执行细节，重启会消失。
  • Task：有身份、状态、历史与管理能力的工作单元。
  • Workflow：多个 Task 的依赖、分支与编排。
Task 边界与生命周期

要理解：哪些工作需要 Task，哪些只是一次普通请求或内部短步骤。

学习成果：能解释 Task 为什么需要身份、归属、输入、状态、结果与历史。

状态机与执行事实

要理解：排队、运行、成功、失败、等待重试、取消请求和已取消的不同含义。

学习成果：能画出状态图，并说明哪些状态转换合法、哪些状态是终态。

Worker、领取与租约

要理解：多个 Worker 怎样避免重复执行，崩溃后怎样让遗留工作重新被处理。

学习成果：能解释原子领取、短事务、租约、续租和过期 Worker 保护。

幂等、重试、取消与恢复

要理解：重复提交、网络超时、临时失败、运行中取消和服务重启时的真实语义。

学习成果：理解为什么多数系统追求“至少一次执行”，业务副作用必须幂等。

结果、权限、审计与观测

要理解：用户应该看到什么、哪些信息不能暴露、怎样判断任务系统是否健康。

学习成果：能列出状态查询、进度、结果引用、权限边界、审计事件和关键指标。

Task 与 Workflow 的边界

要理解：多步骤不等于 Workflow；只有步骤需独立等待、重试、审批或复用时，才需要上升为编排。

学习成果：能说明何时保持一个 Task，何时才值得设计多个 Task 或 Workflow。

核心判断

学习 Task 时，始终守住三件事

先定语义，再选技术

先定义状态、失败、重试和取消的真实含义；不要先从某个框架、队列或数据库语法开始。

状态是事实，不是展示文字

任务状态会影响能否领取、取消、重试和查询结果，因此必须有明确规则和可追溯历史。

可靠性来自组合

幂等、短事务、原子领取、租约、错误分类、退避和审计共同构成可靠性，没有单一万能机制。

学习自查

学完一节后，用这些问题检查理解

能够清楚回答这些问题，比记住某个框架命令更重要。

  • 为什么一个进程内协程不等于可管理的业务 Task？
  • 为什么运行中的任务不能直接标记为“已取消”？
  • 两个 Worker 同时看到同一条待处理任务时，会发生什么？
  • 为什么 Worker 崩溃后不能让任务永久停在运行中？
  • 为什么“消息已经被消费”不等于“业务已经成功完成”？
  • 相同幂等键但不同输入，系统为什么应拒绝而不是复用？
  • 哪些失败应自动重试，哪些失败应直接结束？
  • 什么时候多步骤工作仍应保持为一个 Task，而不是 Workflow？
