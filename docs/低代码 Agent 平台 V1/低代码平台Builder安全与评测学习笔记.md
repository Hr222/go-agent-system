# 低代码平台 Builder、安全与评测学习笔记

> 本文讨论一个低代码 Agent 平台真正面向用户时，需要怎样的 Agent Builder、Workflow Builder、权限、安全、观察和评测能力。

---

## 一、低代码不是“把代码画成方块”

低代码平台的关键是让用户用声明式配置表达执行意图：

```text
我想要一个 Agent
  它使用某个模型
  它遵循某套规则
  它可以查询某个知识库
  它可以调用这些工具
  它输出这种结构

我想要一个 Workflow
  先执行 A
  再把结果交给 B
  如果条件成立走 C
  最后由 D 汇总
```

平台负责把配置转成可执行计划，同时提供校验、权限、版本、运行和调试能力。

如果只是让用户拖几个节点，最后仍然需要开发者手写所有配置，或者节点内部可以执行任意代码，那就不是受控的低代码平台。

## 二、Agent Builder

### 2.1 Agent Builder 的页面区域

一个完整的 Agent Builder 可以包含：

```text
左侧：Agent 基本信息和导航
中间：Prompt / Schema / 测试区
右侧：模型、工具、知识库和运行限制
底部：校验、保存、测试、发布
```

### 2.2 基本信息

用户需要配置：

- 名称。
- 描述。
- 图标或分类。
- 可见范围。
- Agent 的职责说明。
- 输入和输出的使用说明。

描述既服务于用户理解，也可能服务于 Agent 搜索或 Workflow 节点选择。描述不能写成空泛营销文案，应说明能力边界。

### 2.3 Prompt 编辑

Prompt 编辑器应提供：

- System Prompt 编辑。
- 变量列表。
- 可用上下文字段。
- 工具列表和工具说明。
- 禁止使用的内部字段提示。
- 长度和敏感词检查。
- 测试输入。
- Prompt 版本差异。

用户不能在 Prompt 中直接引用数据库连接、文件系统路径、密钥或任意 Python 表达式。

### 2.4 模型配置

模型配置可以包括：

- Provider。
- Model。
- Temperature。
- 最大输出长度。
- 超时。
- 最大调用次数。
- 成本预算。

平台应只展示允许用户选择的模型档案，不直接暴露 Provider 密钥或内部连接配置。

### 2.5 工具和知识库选择

选择器需要展示：

- 工具名称和描述。
- 输入输出 Schema。
- 所需权限。
- 是否需要确认。
- 是否有副作用。
- 当前版本和状态。
- 当前用户是否有权使用。

知识库选择器需要展示：

- 知识库名称。
- 发布版本。
- 可用范围。
- 检索策略。
- 是否必须引用。

### 2.6 Playground

Playground 不是简单的聊天框，它应该用于验证 Agent 定义：

- 使用草稿配置进行测试。
- 显示输入和结构化输出。
- 显示工具调用摘要。
- 显示知识证据和引用。
- 显示错误和重试。
- 显示耗时和成本摘要。
- 允许多组固定测试输入。
- 测试不会自动修改已发布版本。

### 2.7 发布交互

发布按钮应触发服务端校验，而不是只检查前端字段：

```text
点击发布
  -> 服务端读取草稿
  -> 校验模型、Schema、工具、知识库和权限
  -> 生成不可变 Version
  -> 返回发布结果
```

## 三、Workflow Builder

### 3.1 编辑器组成

```text
节点面板 | 画布 | 节点 Inspector
                 |
                 +-- 输入字段
                 +-- 输出字段
                 +-- 工具 / Agent 引用
                 +-- 重试 / 超时
                 +-- 条件和映射
```

### 3.2 最小节点集合

V1 可以从这些节点开始：

- Input Node。
- Agent Node。
- Knowledge Node。
- Tool Node。
- Condition Node。
- Join / Aggregate Node。
- Output Node。

每个节点必须有稳定类型、输入输出端口和可校验配置。

### 3.3 节点编辑

用户选择一个 Agent Node 时，Inspector 应能配置：

- 使用的 Agent Version。
- 输入字段映射。
- 输出字段声明。
- 超时。
- 最大重试次数。
- 失败策略。
- 是否允许异步。

不要让 Inspector 直接展示 Python 类路径或内部 `dispatch_key`。

### 3.4 连线编辑

连接两个节点时，应检查：

- 源节点确实存在该输出字段。
- 目标节点确实需要该输入字段。
- 类型是否兼容。
- 是否重复绑定。
- 是否产生环。
- 是否绕过了必需的审核或权限节点。

### 3.5 流程校验提示

错误应该定位到节点或边：

```text
节点「内容生成」：缺少必填输入 requirements
连线「分析 -> 生成」：字段 evidence 类型不兼容
节点「审核」：没有可达的后继节点
Workflow：检测到循环 A -> B -> A
```

不能只返回“Workflow 不合法”。

### 3.6 测试运行

测试运行需要区分：

- Draft Test：使用当前未发布草稿。
- Published Run：使用已发布版本。

测试运行应使用受控输入和测试权限，必要时屏蔽高风险副作用工具，或要求显式确认。

## 四、权限模型

### 4.1 多层权限

低代码平台至少有这些判断：

```text
用户能否看见 Agent
  -> 用户能否编辑 Agent
  -> 用户能否发布 Agent
  -> 用户能否运行 Agent
  -> Agent 能否使用某个 Tool
  -> Agent 能否访问某个 Knowledge Base
  -> Workflow 能否引用 Agent
  -> 当前 Run 能否读取输入和结果
```

这些判断不能合并为一个“有权限”布尔值，否则很难表达最小权限。

### 4.2 Owner 与 Permission

- Owner 表示资源属于谁或哪个租户。
- Permission 表示主体能做什么。
- Role 表示一组权限。
- Visibility 表示资源是否可被发现。

客户端提交的 owner、角色和权限字段不能作为授权事实。服务端必须从可信请求主体解析这些信息。

### 4.3 发布权限

创建 Agent 的用户不一定可以发布到组织范围。可以区分：

- 私人草稿。
- 团队草稿。
- 已发布的团队 Agent。
- 平台内置 Agent。

发布流程可以需要管理员审批，特别是包含外部副作用工具的 Agent。

## 五、安全：Prompt Injection 与工具安全

### 5.1 不可信内容的来源

Agent 可能读取：

- 用户输入。
- 上传文档。
- 知识库原文。
- 搜索结果。
- 外部 API 响应。
- 其他 Agent 输出。

这些内容都可能包含诱导模型违反原规则的文字。平台必须在架构上承认“模型上下文中的内容不等于系统指令”。

### 5.2 防护方式

- 结构化区分指令、用户数据和工具结果。
- 服务端限制工具权限。
- 对高风险动作要求确认。
- 对工具参数做资源归属校验。
- 不把秘密放进 Prompt。
- 对下游 Agent 只传递最小必要字段。
- 保存来源和证据引用。
- 对关键结论执行确定性校验或人工审核。

### 5.3 任意 URL 和 SSRF

如果允许用户配置 HTTP Tool，需要防止：

- 访问内网地址。
- 访问云元数据服务。
- 读取本机管理接口。
- 通过重定向绕过域名白名单。
- 将内部凭据发送到外部地址。

因此 HTTP Tool 需要域名、协议、端口、网络范围、重定向和响应大小策略。

### 5.4 Secrets

凭据应：

- 加密存储。
- 只在执行器内部注入。
- 不进入 Prompt。
- 不进入普通事件。
- 不进入前端返回。
- 不进入错误堆栈。
- 支持轮换和撤销。

### 5.5 高风险工具确认

确认信息应该说明：

- 将调用哪个工具。
- 将作用于什么资源。
- 主要参数摘要。
- 可能产生什么后果。
- 确认是否只对本次调用有效。

用户确认一个工具不代表允许 Agent 在后续无限调用同一工具。确认范围需要明确。

## 六、运行观察和调试

### 6.1 用户需要看到什么

普通用户通常关心：

- 当前流程状态。
- 当前进行到哪个阶段。
- 是否正在等待输入或审核。
- 是否失败以及是否可重试。
- 最终结果和结果资源。

### 6.2 开发者需要看到什么

开发者还需要：

- 使用的 Agent Version。
- 节点输入输出摘要。
- 工具调用。
- 知识召回和引用。
- 模型调用次数。
- 延迟和 Token。
- 重试原因。
- 分支选择。
- 失败堆栈的受控内部版本。

### 6.3 公开投影与内部记录

```text
公开投影：
  安全状态、摘要、结果引用、可读错误

内部记录：
  调试元数据、调用链、Provider 错误分类、成本和性能信息
```

即使是内部记录，也要遵守最小化和脱敏原则。

### 6.4 运行可复现

要复现一次运行，至少需要：

- Workflow Version。
- Agent Version。
- Tool / Knowledge 版本。
- 输入指纹和安全引用。
- 关键运行参数。
- 条件分支结果。
- 随机性和模型配置摘要。

不能只保存最终文本。

## 七、评测 Agent

### 7.1 为什么需要评测

模型输出具有概率性。Prompt 改动、模型切换、知识库更新和工具变化都可能改变行为。只依靠人工临时点几下无法判断系统是否真的变好。

### 7.2 测试数据集

一个 Agent 评测集可以包含：

- 输入。
- 期望输出结构。
- 必须包含的字段。
- 必须引用的证据。
- 禁止出现的内容。
- 允许的误差。
- 权限或拒答预期。

### 7.3 评测指标

根据 Agent 类型选择：

- 结构化输出通过率。
- 工具选择准确率。
- 参数正确率。
- 任务完成率。
- 证据引用正确率。
- 事实一致性。
- 拒答准确率。
- 平均延迟。
- P95 延迟。
- 平均 Token 和成本。
- 重试率。
- 人工修正率。

### 7.4 Agent-as-Judge 的风险

使用另一个模型评分可以降低人工成本，但评分模型也会犯错。重要任务应结合：

- 确定性字段比较。
- 引用存在性检查。
- 规则校验。
- 人工抽检。
- 多次运行稳定性。

## 八、评测 Workflow 和多 Agent

### 8.1 Workflow 评测矩阵

至少覆盖：

| 场景 | 要证明的事实 |
| --- | --- |
| 全部成功 | 节点按依赖执行并得到结果 |
| 节点失败 | 失败位置和错误可追踪 |
| 瞬时错误 | 按策略重试 |
| 永久错误 | 不无限重试 |
| 并行成功 | 汇总等待正确 |
| 部分失败 | 处理策略符合定义 |
| 条件分支 | 只执行正确路径 |
| 取消 | 运行中的节点协作停止 |
| 重启恢复 | 不重复污染结果 |
| 版本变更 | 旧运行仍使用旧版本 |
| 权限不足 | 运行前或节点执行前被阻止 |

### 8.2 多 Agent 评测

要评测的不只是最终答案，还包括：

- 分工是否正确。
- 是否选择正确的 Agent。
- 是否传递了完整必要字段。
- 是否传播了不必要的敏感字段。
- 是否出现无限委派。
- 是否在预算内结束。
- 汇总是否正确处理冲突。
- 审核是否阻止错误结果。

### 8.3 Baseline

先记录当前版本结果，再比较新版本：

```text
Agent v1：结构化通过率 82%，引用正确率 74%，平均耗时 8s
Agent v2：结构化通过率 90%，引用正确率 86%，平均耗时 11s
```

v2 不是所有指标都必须提高，但必须清楚知道成本、延迟和正确率之间的取舍。

## 九、V1 的用户闭环

一个真正可验收的低代码 Agent 平台 V1，至少要让用户完成：

```text
创建 Agent
  -> 配置 Prompt、模型、知识和工具
  -> 测试
  -> 发布 Agent v1

创建第二个 Agent
  -> 发布 Agent v1

创建 Workflow
  -> 添加两个 Agent 节点
  -> 配置字段映射
  -> 发布 Workflow v1

运行 Workflow
  -> 查看节点状态
  -> 查看失败和重试
  -> 查看最终结果
```

Tender 可以作为内置模板和平台验证案例，但不能因为 Tender 固定流程能运行，就认为用户自定义闭环已经成立。

## 十一、掌握标准

能够独立说明：

1. 低代码平台为什么必须有 Builder、校验、发布和运行观察。
2. Agent Builder 和 Workflow Builder 的职责区别。
3. 用户权限、Agent 权限、Tool 权限和资源 owner 的区别。
4. Prompt Injection、工具注入、SSRF 和 Secret 泄露的基本风险。
5. 普通用户和开发者需要看到的运行信息有什么不同。
6. 如何建立 Agent、Workflow 和多 Agent 的评测集。
7. 如何用 baseline 判断版本升级是否真的变好。
8. 为什么当前静态 Workflow 页面不等于低代码编排器。
