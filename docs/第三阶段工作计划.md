# 第三阶段工作计划

> 状态更新（2026-07-30）：Tender Agent V1.1 已进入分块实现与验收阶段。本阶段包含单个 Agent 的同步招标文件分析、投标书骨架生成、Tender HTTP 接口，以及为后续 SubAgent 编排准备的标准 MCP 能力适配。50MB 以内 DOCX 统一分块，70MB 为服务端硬拒绝线。MCP 只作为能力入口，不包含 Agent Runtime、SubAgent 编排、Task Management、Conversation / Context Management 或 V2 公司资料填充。

本文档是 **Agent Phase 3 的前后端联合执行蓝本**。它在项目刚开始接入 OpenSpec、既有归档和规格尚不完整的过渡期内，统一记录本阶段的范围、实际进度、剩余工作和验收标准。

Phase 3 完成前，开发、评审和验收以本文档为详细依据，同时遵守：

2. `ARCHITECTURE.md`：后端架构基准和依赖边界。
3. `FRONTEND_ARCHITECTURE.md`：前端工程与分层边界。
4. `docs/go agent system - 系统看板.md`：项目高层阶段看板。

本文档把前端与后端工作汇总为同一套范围、依赖和验收标准，并由 [第三阶段- 前后端联合工作进度.md](第三阶段-%20前后端联合工作进度.md) 记录实现、测试、联调和人工验收证据。两份文档的范围与状态必须保持一致；每个工作项按一个前后端垂直切片交付。

## 2. 阶段定位与终点

Phase 3 是 Go Agent System 的首个真实单 Agent 业务验证阶段。投标助手是验证场景，不是平台的长期产品边界。

本阶段终点是完成一次真实、同步的 Tender Agent 调用：

```text
招标文件 + 用户关注点
  -> 请求级隔离解析
  -> Tender Application 调用 Structured LLM
  -> 生成符合招标要求的结构化投标书骨架
  -> 输出骨架文件并在前端展示结果
```

这证明平台已具备“一个独立业务 Agent 复用文件解析与 LLM 能力完成真实调用，并产出可供后续 Agent 继续处理的业务结果”的基础，为下一阶段 SubAgent 编排做准备；不代表平台已经具备多 Agent 编排、任务运行时或会话上下文能力。

## 4. 本阶段范围

### 4.1 必须交付

| 联合切片 | 后端责任 | 前端责任 | 完成结果 |
| --- | --- | --- | --- |
| 输入与契约 | 定义一次同步分析的 multipart HTTP Schema、Application Command/Result、错误契约和依赖组装。 | 提供招标文件选择、用户关注点输入、本地格式和大小提示。 | 用户可提交一个有效文件和关注点。 |
| 请求级解析 | 在受控临时目录中完成文件校验、解析、文本限额和清理。 | 展示提交中状态与可理解的解析失败信息。 | 文件不进入政策知识库，也不形成持久任务。 |
| 结构化分析与骨架生成 | Tender Application 组织 Prompt，通过已有 Structured LLM Port 提取招标要求、章节结构和风险点，并通过骨架渲染能力输出文件。 | 通过统一 HTTP Client 提交请求，不直接接触模型、解析器或领域对象。 | 返回有边界、有结构、可供后续填充的投标书骨架。 |
| 公司资料库填充 | 不属于本阶段；待公司资料准备后作为 V2 迭代接入已发布知识库和引用能力。 | 不属于本阶段。 | 不将当前已有的行政类测试数据冒充为 Tender 公司资料。 |
| 联调与验收 | 覆盖 Application、HTTP、解析、结构化 LLM、文件渲染 Fake 和错误分支。 | 覆盖 API/Hook/页面状态、骨架预览或下载，完成构建和浏览器人工验证。 | 一条真实同步链路在前后端均可验证。 |

### 4.2 明确不做

以下能力不属于 Phase 3，不能为了“页面看起来完整”而提前实现：

- `task_id`、任务创建、状态查询、轮询、重试、取消、任务级下载、持久化和恢复。
- 会话历史、上下文记忆、会话持久化或恢复。
- Agent Runtime、LangGraph、Function Calling、SubAgent 或多 Agent 编排；MCP 能力适配属于本阶段，但不实现 MCP 编排。
- 招标文件入库、政策知识库写入或长期保存原始招标文件。
- 公司资料库检索、资料不足判断、公司能力匹配、建议生成和骨架内容填充；这些属于后续 V2。
- 基于骨架生成完整投标正文、人工确认和编辑工作流。
- 将 `/agents/tender/tasks/*` 的 Mock 页面接入真实接口。

`Task Management`、`Conversation / Context Management` 与未来 Agent 编排均是平台独立模块；它们将在后续阶段通过独立的 OpenSpec Change 设计，不内嵌在 Tender Agent 或 LLM 模块中。

## 5. 架构与实现约束

```text
TenderPage
  -> HTTP Tender Route / Schema / Assembler
  -> Tender Application Use Case
       -> 请求级文件解析 Port
       -> Structured LLM Port
       -> Skeleton Document Renderer Port
  <- 文件解析实现 / 文件渲染实现 / LangChain LLM Adapter
  -> HTTP Response（结构化骨架 + 骨架文件）
```

- HTTP 层只处理 multipart 协议、Schema、Assembler、依赖注入和异常映射；不得直接调用 LangChain、Repository 或文件解析器。
- Tender Application 负责一次调用的业务编排、Prompt 输入准备、结果校验和错误转换；不得创建具体 SDK 客户端或读取环境变量。
- Tender Domain/Ports 只表达业务输入、输出及依赖契约；不得依赖 FastAPI、数据库、LangChain 或具体供应商 SDK。
- 文件处理只使用请求级临时资源；无论成功、失败或客户端中断均要清理。
- V1 不依赖公司知识库，不将招标文件写入政策知识库；招标文件来源定位只来自当前请求文件。
- 结构化 LLM 仅对招标文本和用户关注点给出受 Schema 约束的要求、章节和风险点，不生成公司事实或无来源的响应内容。
- 骨架文件由独立渲染端口生成，领域和应用层不依赖 DOCX 库或具体文件格式。
- 前端新增 `features/agent/tender/` 的真实单页模块并替换 `/agents/tender` 路由。现有 Mock 工作台可保留为后续视觉原型，但不得作为本阶段真实状态来源。

## 7. 验收标准

### 自动化与架构验收

- 有效的脱敏或合成文件和非空关注点可通过真实 HTTP 契约进入 Tender Application。
- 空文件、格式/大小超限、解析失败、模型配置缺失、上游失败、文件渲染失败和结构化输出不合法均有稳定、可理解的响应。
- 测试使用文件解析、Structured LLM 和文件渲染的可控替身；不依赖真实模型或公司资料即可覆盖成功与失败分支。
- 解析临时文件在成功和异常分支都被清理，且招标文件不会写入政策知识库。
- 骨架中的要求、章节和风险点能够追溯到招标文件的页码、章节或其他可用位置；本阶段不要求公司知识库引用。
- Domain/Application 不依赖 FastAPI、LangChain 或前端类型；HTTP Route 不直接编排模型或 Repository。
- 后端相关测试、`ruff check app tests`、`python -m compileall -q app tests` 通过；前端测试与 `npm run build` 通过。

### 前后端人工验收

1. 打开 `/agents/tender`，选择一个支持的测试文件并输入关注点。
2. 点击一次提交，页面在同页展示处理中状态，不生成任务 ID，也不跳转任务详情页。
3. 成功时展示结构化分析结果、关键要求、风险点，并提供骨架文件预览或下载。
4. 解析失败、模型失败或文件生成失败时展示明确错误，页面可重新提交。
5. 刷新页面后不承诺保存此前的 Tender 请求或结果。

满足以上标准，即可宣布 Phase 3 完成；不能以“已有 Mock 页面”或“模型曾返回文本”替代整条链路的验收。
