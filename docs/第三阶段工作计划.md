# 第三阶段工作计划

## 1. 文档定位

本文档是 **Agent Phase 3 的前后端联合执行蓝本**。它在项目刚开始接入 OpenSpec、既有归档和规格尚不完整的过渡期内，统一记录本阶段的范围、实际进度、剩余工作和验收标准。

Phase 3 完成前，开发、评审和验收以本文档为详细依据，同时遵守：

1. `agent.md`：协作与工程开发约定。
2. `ARCHITECTURE.md`：后端架构基准和依赖边界。
3. `FRONTEND_ARCHITECTURE.md`：前端工程与分层边界。
4. `docs/go agent system - 系统看板.md`：项目高层阶段看板。

本文档把前端与后端工作汇总为同一套范围、依赖和验收标准，并由 [第三阶段- 前后端联合工作进度.md](第三阶段-%20前后端联合工作进度.md) 记录实现、测试、联调和人工验收证据。两份文档的范围与状态必须保持一致；每个工作项按一个前后端垂直切片交付。

Phase 3 完成、结论和必要证据已提炼后，两份阶段文档一并删除；后续阶段的详细需求、设计、任务和验收统一从 OpenSpec Change 开始管理，系统看板只保留高层方向与状态。

## 2. 阶段定位与终点

Phase 3 是 Go Agent System 的首个真实单 Agent 业务验证阶段。投标助手是验证场景，不是平台的长期产品边界。

本阶段终点是完成一次真实、同步的 Tender Agent 调用：

```text
招标文件 + 用户关注点
  -> 请求级隔离解析
  -> 检索已发布知识库中的 RAG 内容
  -> Tender Application 调用 Structured LLM
  -> 返回含真实来源引用的结构化结果
  -> 前端在同一页面展示结果、错误和引用
```

这证明平台已具备“一个独立业务 Agent 复用文件解析、RAG 与 LLM 能力完成真实调用”的基础，而不代表平台已经具备多 Agent 编排、任务运行时或会话上下文能力。

## 4. 本阶段范围

### 4.1 必须交付

| 联合切片 | 后端责任 | 前端责任 | 完成结果 |
| --- | --- | --- | --- |
| 输入与契约 | 定义一次同步分析的 multipart HTTP Schema、Application Command/Result、错误契约和依赖组装。 | 提供招标文件选择、用户关注点输入、本地格式和大小提示。 | 用户可提交一个有效文件和关注点。 |
| 请求级解析 | 在受控临时目录中完成文件校验、解析、文本限额和清理。 | 展示提交中状态与可理解的解析失败信息。 | 文件不进入政策知识库，也不形成持久任务。 |
| RAG 与结构化分析 | 复用已发布知识库检索与引用；由 Tender Application 组织 Prompt，并通过已有 Structured LLM Port 完成一次调用和 Schema 校验。 | 通过统一 HTTP Client 提交请求，不直接接触模型、检索或领域对象。 | 返回有边界、有结构的分析结论。 |
| 结果与引用 | 将检索来源转换为稳定响应字段；禁止模型伪造文件、页码或引用。 | 在提交页展示结论、引用、无结果和错误状态。 | 用户可以查看每条引用的来源信息。 |
| 联调与验收 | 覆盖 Application、HTTP、解析、检索、LLM Fake 和错误分支。 | 覆盖 API/Hook/页面状态，完成构建和浏览器人工验证。 | 一条真实同步链路在前后端均可验证。 |

### 4.2 明确不做

以下能力不属于 Phase 3，不能为了“页面看起来完整”而提前实现：

- `task_id`、任务创建、状态查询、轮询、重试、取消、下载、持久化和恢复。
- 会话历史、上下文记忆、会话持久化或恢复。
- Agent Runtime、LangGraph、Function Calling、MCP、SubAgent 或多 Agent 编排。
- 招标文件入库、政策知识库写入或长期保存原始招标文件。
- 投标书章节骨架、正文生成、文件导出、人工确认和编辑工作流。
- 将 `/agents/tender/tasks/*` 的 Mock 页面接入真实接口。

`Task Management`、`Conversation / Context Management` 与未来 Agent 编排均是平台独立模块；它们将在后续阶段通过独立的 OpenSpec Change 设计，不内嵌在 Tender Agent 或 LLM 模块中。

## 5. 架构与实现约束

```text
TenderPage
  -> HTTP Tender Route / Schema / Assembler
  -> Tender Application Use Case
       -> 请求级文件解析 Port
       -> 已发布知识库检索能力
       -> Structured LLM Port
  <- 文件解析实现 / 检索实现 / LangChain LLM Adapter
  -> HTTP Response（结构化结论 + 真实引用）
```

- HTTP 层只处理 multipart 协议、Schema、Assembler、依赖注入和异常映射；不得直接调用 LangChain、Repository 或文件解析器。
- Tender Application 负责一次调用的业务编排、Prompt 输入准备、结果校验和错误转换；不得创建具体 SDK 客户端或读取环境变量。
- Tender Domain/Ports 只表达业务输入、输出及依赖契约；不得依赖 FastAPI、数据库、LangChain 或具体供应商 SDK。
- 文件处理只使用请求级临时资源；无论成功、失败或客户端中断均要清理。
- 只检索已发布知识库。引用必须来自检索结果的稳定元数据，而非模型生成的引用文本。
- 结构化 LLM 仅对输入的招标文本、关注点和 RAG 上下文给出受 Schema 约束的分析结果；资料不足时明确返回缺失或不确定性。
- 前端新增 `features/agent/tender/` 的真实单页模块并替换 `/agents/tender` 路由。现有 Mock 工作台可保留为后续视觉原型，但不得作为本阶段真实状态来源。

## 6. 联合执行顺序

| 顺序 | 联合工作项 | 交付与检查 |
| --- | --- | --- |
| 1 | 收口现有 Chat 流式 Change | 按时间顺序同步三个已完成 Change 的增量规格并归档，避免主规格与已验证行为不一致。 |
| 2 | 固定同步调用契约 | 确定文件类型/大小、关注点字段、文本与上下文限额、响应 Schema、引用字段、超时与错误映射；前后端共用该契约。 |
| 3 | 实现 Tender 后端垂直能力 | 完成 Command/Result、临时解析、检索调用、Structured LLM 调用、真实引用组装、Composition Root、HTTP Route 与离线测试。 |
| 4 | 实现 Tender 前端单页 | 实现 API、Hook、文件/关注点表单、提交中、成功、资料不足、解析失败、模型失败和引用展示。 |
| 5 | 联调与验收 | 使用合成或脱敏招标文件完成真实调用；执行自动化检查、前端构建与浏览器人工验证。 |
| 6 | 记录本阶段结论 | 更新本文件的状态、验证证据和遗留事项；Phase 3 完成后不再在此扩展下一阶段需求。 |

第 1 项是既有 Change 的流程收口，不改变 Tender 功能范围；第 2 至第 5 项共同构成本阶段剩余交付。

## 7. 验收标准

### 自动化与架构验收

- 有效的脱敏或合成文件和非空关注点可通过真实 HTTP 契约进入 Tender Application。
- 空文件、格式/大小超限、解析失败、知识库无可用来源、模型配置缺失、上游失败和结构化输出不合法均有稳定、可理解的响应。
- 测试使用文件解析、检索和 LLM 的可控替身；不依赖真实模型或生产资料即可覆盖成功与失败分支。
- 解析临时文件在成功和异常分支都被清理，且招标文件不会写入政策知识库。
- 返回的引用可追溯到检索结果的文档、版本、章节、页码、原文片段和文件信息（可用字段以现有数据为准）。
- Domain/Application 不依赖 FastAPI、LangChain 或前端类型；HTTP Route 不直接编排模型或 Repository。
- 后端相关测试、`ruff check app tests`、`python -m compileall -q app tests` 通过；前端测试与 `npm run build` 通过。

### 前后端人工验收

1. 打开 `/agents/tender`，选择一个支持的测试文件并输入关注点。
2. 点击一次提交，页面在同页展示处理中状态，不生成任务 ID，也不跳转任务详情页。
3. 成功时展示结构化分析结论和真实知识库引用；引用信息可供用户辨识来源。
4. 无资料、解析失败或模型失败时展示明确错误/资料不足提示，页面可重新提交。
5. 刷新页面后不承诺保存此前的 Tender 请求或结果。

满足以上标准，即可宣布 Phase 3 完成；不能以“已有 Mock 页面”或“模型曾返回文本”替代整条链路的验收。
