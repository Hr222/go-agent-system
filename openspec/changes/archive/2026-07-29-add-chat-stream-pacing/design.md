## Context

`useDeltaRenderQueue` 已经保证 Provider `delta` 不会被 React 同批更新覆盖，但一个 `delta` 本身可能包含几十个字符。真实 Provider 在首片段后集中返回时，用户仍会看到整段文本快速出现。

本变更只影响浏览器中已经接收的文本如何显示。网络读取、SSE 事件、取消传播和模型调用保持不变。

## Goals / Non-Goals

**Goals:**

- 将接收的文本按用户可读的字符组持续显示，形成清晰的输出过程。
- 保持所有字符、空白和标点的原始顺序，最终内容与收到的 `delta` 拼接结果完全一致。
- 在大量积压或流结束时自动增加每次提交量，使本地展示在有限时间内赶上网络内容。
- 完成、取消和失败继续在已接收文本显示完毕后更新最终状态。

**Non-Goals:**

- 不调整 Provider 分块、首 Token 延迟、HTTP 超时或后端配置。
- 不改变回答文本、内容安全策略、Token 计量或 API 契约。
- 不加入可供用户配置的速度设置、第三方动画库或持久化偏好。

## Decisions

### 1. 按 Unicode 可读字符组拆分展示单元

渲染队列将每个 `delta` 拆成 Unicode 字素簇（grapheme cluster）。优先使用浏览器原生 `Intl.Segmenter`，不可用时退回 `Array.from`。这样中文、拉丁文字、标点和组合 Emoji 不会在常见浏览器中被拆成不可读的半个字符。

选择字素簇而不是按字节、UTF-16 code unit 或词语拆分：前两者会破坏 Unicode，词语又不能稳定适配中英文混合内容。

### 2. 使用固定节奏与自适应排空相结合

队列在首个展示单元到达时立即安排绘制，后续以约 30ms 的最小间隔提交。常规积压每次显示少量字符组；当待显示字符组较多时，每次提交量按目标排空帧数自动增大，使队列在约一秒内赶上，而不是让长回答持续数十秒的动画。

选择有界加速而不是纯逐字定时：它保留短回答和小片段的可见节奏，同时限制快速 Provider 或网络恢复时的额外等待。展示队列始终按原始顺序取出单元，不会合并、删除或重排文本。

### 3. 终止事件与展示队列保持同一生命周期

`complete`、取消和失败仍只记录终止意图。队列排空后在下一次绘制时提交最终状态；取消或失败不会丢弃已在本地队列中的字符组。输出指示在该时刻停止。

这保留上一变更的状态语义，并确保用户不会看到“已完成”但最后一段文字尚未出现。

## Risks / Trade-offs

- [动画增加最终文本出现的延迟] → 首单元立即绘制，并使用积压自适应批量和有限目标排空时间。
- [字符分割在旧浏览器不一致] → 使用 `Intl.Segmenter` 并提供 `Array.from` 退回路径；最终文本按原始字符序列追加。
- [取消或组件卸载后定时器继续执行] → 队列同时管理计时器和动画帧，并在开始新请求及卸载时取消。
- [单测依赖时间] → 注入或模拟计时器和动画帧，测试顺序、批量加速和终止排空，不依赖真实等待。

## Migration Plan

1. 扩展现有渲染队列，增加字素分割、节奏调度和积压加速。
2. 更新队列测试与 Chat 页面状态测试。
3. 执行前端测试和生产构建，并使用本地多片段 SSE 验证中间文本可见。
4. 若展示节奏不符合预期，可仅移除节奏调度，回退到上一版本的动画帧级 `delta` 追加；后端无需回滚。
