## Why

当前 `POST /api/v1/llm/chat` 采用同步聚合调用，必须等待模型生成完整回答后才返回，前端也只能在整个请求结束后展示内容。现在需要为现有的单轮 LLM 对话建立端到端的流式交付能力，让用户能够逐步看到回答，同时保证旧客户端、错误处理和生产运行边界不被无意破坏。

## What Changes

- 为现有 `llm-chat` 增加独立的流式 HTTP 入口，让客户端可以按生成进度接收回答内容；具体传输协议和路径在 design 阶段确定。
- 保留现有 `POST /api/v1/llm/chat` 及其一次性 JSON 响应契约不变，避免已有客户端被迫迁移；流式能力只通过新的入口提供。
- 明确流式请求从建立、开始输出、持续增量、正常完成，到上游失败、客户端取消、服务端断连和超时的完整生命周期。
- 调整后端的 Application、LLM Port、模型适配器和 HTTP 响应处理，使流式调用沿现有 `Interfaces -> Application -> Ports -> Infrastructure` 依赖方向传递，并能够释放取消请求占用的上游资源。
- 调整前端 Chat 请求层和页面状态：创建生成中的助手消息，按顺序追加增量内容，正常结束后补充模型和 Token 信息；部分输出失败或用户取消时保留已接收内容，并支持基于原始消息的显式重试。
- 适配流式请求的连接保持、超时、代理缓冲、并发限制、资源释放、日志、指标和敏感信息保护，保证开发环境与生产运行环境都能验证流式行为。
- 增加后端、前端、HTTP、集成和运行环境验收，并保留旧 JSON 接口的回归验证。
- 保留单轮请求、Prompt 版本、模型标识和 Token 使用信息；不引入会话历史、上下文记忆、工具调用、知识库引用、Agent 编排或回答持久化。

## Capabilities

### New Capabilities

无。本次变更是在现有 `llm-chat` 能力上增加流式交付入口和对应的前端交互行为，不单独创建新的业务能力规格。

### Modified Capabilities

- `llm-chat`：在保留原有一次性 JSON 契约的基础上，增加流式响应契约，并修改前端单轮请求的消息生命周期、取消、失败恢复和完成状态。

## Impact

- HTTP 契约：保留现有 `POST /api/v1/llm/chat` 的请求和响应行为，新增独立的流式 HTTP 入口；流开始前后的错误表达、结束语义和兼容策略需要重新定义。
- 后端模块：影响 `app/modules/llm` 的 Application 与 Port、`app/infrastructure/llm` 的模型适配器、`app/interfaces/http` 的路由和流式响应处理，以及 `app/composition` 中的依赖组装。
- 外部 Provider：需要评估 Provider 原生异步流能力、连接复用、连接关闭、首 Token 和空闲超时，以及 Token 使用信息在流结束时是否可获得。
- 前端模块：影响 `frontend/src/features/chat` 的 API 调用、流读取、增量内容拼接、助手消息状态、取消、自动滚动、完成态、部分失败和显式重试；现有 Axios 一次性 JSON 调用不能直接承担全部流式接收职责。
- 运行环境：当前仓库缺少流式生产代理、限流和指标配置，需要评估反向代理缓冲、连接保持、响应超时、心跳和并发流限制对流式交付的影响。
- 可观测性与安全：需要记录请求标识、阶段、首 Token 延迟、总耗时、结束原因、事件数量、活跃流数和错误码等运行信息，同时不得记录 Prompt、增量内容、鉴权信息、API Key 或未经审查的上游异常。
- 资源治理：客户端取消、服务端断连、Provider 超时和容量耗尽都必须释放流连接、Provider 调用和并发配额，避免请求泄漏、重复计费或无限占用资源。
- 测试与验收：补充 Port、Adapter、Application、HTTP、前端状态和集成测试，覆盖首内容前失败、部分输出后失败、取消、超时、旧 JSON 客户端回归、代理转发和并发限制等场景。
- 持久化与迁移：不修改数据库，不保存会话历史，不新增数据迁移，不持久化流式回答。
- 发布与兼容：采用新增入口、保留旧入口的兼容演进方式；具体灰度、降级和回滚策略在 design 与 tasks 阶段确定。
