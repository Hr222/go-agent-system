## Context

当前 Tender Application 已能解析 DOCX、调用结构化 LLM、校验 `TenderAnalysis` 并生成骨架文件，但它把整份解析文本作为一次模型输入。真实 GLM 诊断显示：网络、Key 和普通 Chat 可用；小型 JSON Object 请求可用；约 40,000 字符的招标分析请求会在读取响应头阶段超时。不同 Provider 的上下文窗口和附件能力不稳定，不能作为 Tender Agent 的前提。

本 Change 只调整 V1 function 的内部分析策略。外部仍然是一次同步的 `tender.generate_bid_skeleton` 调用，结果仍然包含分析和一个或多个 DOCX；它不引入 Agent Runtime、SubAgent 编排、公司资料库或持久化任务。

## Goals / Non-Goals

**Goals:**

- 对 50MB 以内的 DOCX 统一建立请求级证据索引，并按章节、表格和证据边界分块。
- 让每次 LLM 调用都处于可配置的字符/Token、超时和输出预算内。
- 通过分块提取与全局归并完成单卷/多卷判断、关键要求提取、服务交付成果区分和待确认处理。
- 保留每条中间结论和最终结论的源文档证据引用。
- 在某个分块失败、证据不足或 Provider 超时时明确失败或待确认，不静默生成完整结论。
- 保持现有 HTTP、MCP、前端和骨架文件输出契约兼容。

**Non-Goals:**

- 不依赖 Provider 的原生附件上传或超大上下文能力。
- 不支持 100MB、1GB 文件的分片上传、异步任务、断点恢复或持久化索引。
- 不接入公司知识库、V2 内容填充、Conversation、Task Management 或 SubAgent Runtime。
- 不改变投标骨架 Renderer 的模板复制和 DOCX 生成职责。

## Decisions

### 1. 用请求级证据索引作为分块输入

DOCX Reader 输出带有 `evidence_id`、块类型、标题路径、表格信息和顺序的文档块。Chunk Planner 按标题层级和表格边界组合连续块，生成带 `chunk_id`、证据 ID 列表、章节路径、文本和 Token 估算的分块计划。

段落可以按预算切分；表格默认保持完整，超过单块预算时按行组拆分并重复表头。分块不跨越无法解释的章节边界，不把目录名称直接当作投标分线结论。

替代方案是按固定字符数截断整份文本。该方案会破坏表格和章节语义，也会使证据引用无法解释，因此不采用。

### 2. 采用“分块提取 + 全局归并”的两层 LLM 流程

第一层对每个分块只提取局部事实：明确要求、投标文件/分册候选、章节/表格/函件/附件、提交规则、证据引用和待确认项。第一层不最终决定单卷/多卷，也不生成公司事实。

第二层接收压缩后的分块结果和必要的原文证据摘要，负责去重、处理冲突、判断单卷/多卷、区分服务交付成果，并输出现有 `TenderAnalysis`。当分块结果过多时，归并继续使用树形批次归并，不能把所有中间结果再次拼成无界 Prompt。

替代方案是只检索少量相关段落后直接生成最终结果。该方案可能漏掉递交、封装、附件或评审要求；因此检索只能作为归并阶段的证据缩减手段，不能替代全量分块提取。

### 3. 以中间契约隔离 Provider

新增分块提取和归并所需的 Application/Port 契约，不让 HTTP、MCP 或 DOCX Adapter 直接知道 LLM 批次。Provider Adapter 只接收单个受控请求，使用兼容的 JSON Object 返回并在本地执行 Pydantic Schema 校验；最终业务校验仍由 Tender Application 完成。

每个 Provider 调用记录阶段、chunk_id 或归并批次、模型、Prompt 版本、输入/输出长度和耗时，不记录原文、用户关注点、API Key 或生成文件内容。

### 4. 分块失败采用有限重试和失败闭合

单个 Provider 调用只允许配置范围内的有限重试，并区分输入错误、鉴权/契约错误和暂时性超时。分块失败时保留失败批次的诊断标识；如果无法证明要求覆盖完整，Application 不生成看似完整的骨架，而是返回稳定的分析失败或待确认结果。

请求级临时目录和中间结果在成功、异常和客户端中断时清理。V1 不把分块结果写入知识库或持久化任务。

### 5. 文件大小和内容预算分层控制

产品正常接收上限为 50MB；服务端设置 70MB 绝对拒绝线，防止配置错误或绕过前端限制。文件字节数不是唯一预算：还要统计解压大小、块数量、Token 估算、表格规模和总调用预算。50MB 以内的文件也必须经过分块；超过分块预算时返回可解释的输入/分析限制错误。

### 6. 保持协议契约不变

HTTP `/api/v1/agents/tender/skeleton` 和 MCP `tender.generate_bid_skeleton` 继续把一次请求映射为一个 Tender Application Command。成功结果的 `analysis`、`artifacts`、模型和 Prompt 版本字段不变；失败继续映射到现有稳定错误码。前端不展示内部批次，不创建 `task_id`。

## Risks / Trade-offs

- [风险] 多次 LLM 调用增加延迟、费用和 Provider 限流概率。→ 对分块和归并设置并发、总调用数、Token 和总耗时预算；记录批次耗时，失败时不无限重试。
- [风险] 分块边界可能切断跨章节要求。→ 保留标题路径、相邻块关系和证据顺序；对冲突或跨块要求交给归并阶段并标记证据。
- [风险] 某个分块失败会导致整体无法确认。→ 返回失败批次和待确认项，不把不完整结果标记为完成；后续可单独设计可恢复任务。
- [风险] 表格、图片和附件文本可能超过单块预算。→ 表格按行组拆分并重复表头；图片/OCR 和超大附件超出本 Change 范围时明确返回限制错误。
- [风险] 50MB DOCX 解压后可能远大于上传大小。→ 在临时目录中执行压缩包和解压预算校验，并限制文件数量、解压大小和异常压缩比。

## Migration Plan

无数据库迁移。先增加分块契约、Reader 索引和 Fake LLM 测试，再接入真实 Provider Adapter 和 Application 归并，最后执行 20 个 Demo 的真实或脱敏验收。HTTP、MCP 和前端沿用现有接口；如果分块流程未通过验收，可以回滚到当前单次调用实现，但不把未验证结果标记为 V1 完成。

## Open Questions

- 50MB～70MB 的边界是否统一拒绝，还是允许进入受限分析模式；本 Change 只保证 50MB 以内正常路径和 70MB 以上硬拒绝。
- 分块输入和归并输入的初始 Token 预算需要通过 GLM、Fake Provider 和 20 个样本校准，不能在设计阶段假定所有模型相同。
- 当同步请求的分块数量超过总耗时预算时，本 Change 暂返回稳定限制错误；异步可恢复执行另立 Change。
