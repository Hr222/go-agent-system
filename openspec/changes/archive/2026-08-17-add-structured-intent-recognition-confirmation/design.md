## Context

候选召回只能缩小能力范围。系统还需要从用户输入中抽取已提供资料、识别缺失字段并生成用户能确认或取消的提议，但此阶段不能拥有执行权。

## Goals / Non-Goals

**Goals:**

- 使用现有 Structured LLM Port 在候选范围内生成受约束的意图结果。
- 以领域模型表达澄清、未识别、待确认、已确认和已取消的单次交互状态。
- 通过确定性校验阻止目录外能力、禁用能力、缺失资料或权限不满足进入确认。

**Non-Goals:**

- 不创建 HTTP 或前端页面，不调用 Agent、RAG、政策判断或工具。
- 不持久化跨会话确认，不引入 Conversation、Task Management 或 LangGraph。

## Decisions

### 1. LLM 输出必须绑定候选能力代码

请求 Schema 中只允许候选集合中的能力代码；结果包含能力代码、提取输入、缺失输入、澄清原因和置信信息。应用层在接收后再次校验目录状态和输入 Schema，模型输出不是执行授权。

### 2. 规则优先处理确认、取消和无效状态

确认、取消、空输入、候选为空、能力禁用和权限不足由代码处理。只有需要理解自然语言且候选有效时才调用 Structured LLM，降低无意义模型调用并让状态可预测。

### 3. 确认结果只生成受控提议

确认服务返回已批准的能力代码、标准化输入和固定分发键，不能引用 Adapter、URL、函数或类。Dispatcher 由最终集成 Change 实现，当前 Change 不拥有任何执行依赖。

## Risks / Trade-offs

- [模型返回格式不正确或目录外代码] → Schema 校验失败后返回澄清状态，不进入确认。
- [确认状态被误作长期任务] → 领域对象只在当前请求生命周期存在，跨请求恢复另立 Change。
- [确认文案与执行内容不一致] → 确认提议和批准结果均由同一份目录条目生成。

## Migration Plan

在候选召回可用后新增应用服务及单元测试；尚不接入任何现有 Route。出现问题时，统一入口保持不可用，不影响直接业务接口。
