## Context

前四个 Change 分别提供通用向量、能力目录、候选召回、结构化识别和确认提议；独立归档的 `add-request-principal-resolver` 提供可信请求主体解析边界。此 Change 是唯一允许把前四项交互能力暴露给用户并在明确确认后连接到真实业务能力的阶段；它只消费请求主体，不实现认证。

## Goals / Non-Goals

**Goals:**

- 提供统一交互 HTTP 用例与前端确认界面。
- 将确认后的受控提议按目录中的固定分发键路由到 Agent Runtime 或 Online 用例。
- 通过端到端测试证明“未确认、取消、澄清、失败均不执行”。

**Non-Goals:**

- 不替换现有直接 Chat、Agent、RAG 或知识库接口。
- 不引入 Hermes、Fine-tune、持久化确认、任务恢复、动态目录或新 Provider。
- 不实现用户注册、登录、Session、JWT、SSO、角色管理或权限后台。

## Decisions

### 1. 统一入口使用独立 HTTP 契约

新增识别和确认请求；HTTP Schema 经 Assembler 转为 Interaction Application 命令。现有路由不经过网关，从而保持调用方兼容并允许渐进采用。

### 2. 前端只展示应用层返回的受控状态

界面根据识别、澄清、待确认、取消和分发结果渲染；不拼接 Prompt、不解析模型自由文本，也不决定执行目标。确认请求携带应用层生成的提议标识或等价受控数据。

### 3. Dispatcher 采用静态映射并在确认后调用

Dispatcher 使用目录中的固定分发键映射到已组装的 Application Use Case。它在调用前再次验证目录状态、权限和确认结果；没有确认时不持有目标执行器，也不发起后台任务。

### 4. 以端到端场景定义集成完成

至少覆盖 Agent 和非 Agent 目标、缺失资料澄清、取消、确认前拒绝执行、分发失败及既有接口兼容。日志记录能力代码和状态，不记录不必要的原始敏感输入。

### 5. 权限由已归档的请求主体解析插口提供

统一入口通过 HTTP 依赖消费已归档的 `PrincipalResolver` 和 `RequestPrincipal`，将其权限集合传入候选召回、确认和分发前复核。客户端提交的 `permissions`、角色或能力代码均不得作为可信授权来源。当前匿名实现返回空权限集合；未来接入 JWT、Session 或 SSO 时只替换解析器实现。匿名主体只能访问目录中不要求权限的公开能力，受保护 Agent 能力默认拒绝。

### 6. 确认状态使用短期一次性服务端状态

识别请求返回受控 `proposal_id`，服务端在进程内保存短 TTL 提议，并在确认或取消时一次性消费。该状态不写入 Conversation、Task 或数据库，不创建后台任务；未来多实例部署时可将同一端口替换为 Redis 等短期存储。

### 7. 候选索引和目录输入以真实运行契约为准

统一入口在候选索引未就绪时显式刷新当前可用目录，首版优先保证正确性。能力目录的 `input_schema` MUST 与实际 Application Command 对齐，尤其 `policy.review` 使用 `scenario_code`、`submitted_materials`、`top_k`、`document_id` 和 `include_history`，不使用无法映射的 `answers` 别名。

### 8. 意图识别嵌入 Chat，而不是独立用户工作台

统一交互 HTTP 契约保留为服务端内部边界，但前端只保留 Chat 作为用户入口。用户发送消息时，由 Chat 页面后台调用意图识别接口；候选召回、结构化识别和权限过滤不作为独立页面状态展示。只有服务端生成待执行提议后，Chat 才在消息流中展示能力说明和确认/取消操作。

这样可以让意图识别承担类似沙箱批准层的职责：它对用户请求进行规划和拦截，但不会要求用户理解“意图识别”这个平台内部概念。现有直接 Chat、Agent、RAG 和知识库 HTTP 接口仍然保留，旧客户端不需要迁移；新的 Chat 页面优先使用统一入口。

## Risks / Trade-offs

- [确认请求被篡改或重放] → 服务端重新校验目录、输入和确认提议，并采用短生命周期标识或等价受控状态。
- [当前没有用户管理] → 默认匿名主体为空权限，受保护 Agent 能力保持不可用，测试通过覆盖 HTTP 主体解析依赖注入来验证完整分发链路。
- [新增前端流程影响既有工作台] → 将确认交互限制在 Chat 消息流内，移除独立意图识别导航；现有直接 HTTP 接口和其他业务页面保持不变。
- [分发映射遗漏新能力] → 目录构建和 Composition Root 启动时验证分发键均有受控目标。

## Migration Plan

以前四个交互能力 Change 和 `add-request-principal-resolver` 已归档为前提，先后端保留统一入口并在测试环境验证，再由 Chat 页面在发送消息时内部消费该入口。失败时 Chat 可暂时恢复直接 Chat 调用，后端统一入口和既有直连接口无需回滚。

## Open Questions

统一入口放入现有 Chat 页面；独立意图识别工作台仅作为开发调试或验收工具，不作为用户导航入口。
