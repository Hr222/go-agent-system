## Context

既有 `CapabilityCandidateRetrieval` 通过 `CapabilityCatalogPort` 读取可用能力，使用 `TextEmbeddingPort` 构建独立内存索引，并以余弦相似度返回有限候选。该实现已经与政策知识索引隔离，但服务实例在 Composition Root 中共享：`refresh(permissions)` 会以某一主体的权限构建唯一索引，而 `search()` 没有权限参数，无法确认索引是否属于当前主体。

P2.2 位于 V2 Interaction Control 的入口，只负责把“当前主体可看见的能力”缩小为有限候选。它不能决定最终意图、补齐输入、创建确认提议或执行能力。

## Goals / Non-Goals

**Goals:**

- 按规范化权限集合隔离候选索引和查询，阻止跨主体复用候选集合。
- 保留独立内存索引、有限排序结果、检索元数据和 Embedding 故障的显式状态。
- 让现有调用方在构建、就绪检查和查询时传递同一个权限范围。

**Non-Goals:**

- 不接入 V2 Dialogue Runtime，不调用结构化 LLM，不进行最终意图识别或澄清文案生成。
- 不修改目录持久化、引入 pgvector、Redis、数据库表、HTTP 接口或前端。
- 不建立确认提议、结构化 Agent Call、授权策略或实际分发。

## Decisions

### 1. 使用规范化权限集合标识内存索引范围

服务将权限字符串去空白、去重并排序，得到稳定的权限范围键。每个范围拥有独立的 `InMemoryCapabilityCandidateIndex`；`refresh` 只从该范围可见的目录条目构建或替换对应索引，`search` 也只读取同一范围的索引。

替代方案是维护一个全局索引并在查询后过滤。目录端口没有提供忽略权限的安全读取契约，且全局索引可能把受限能力代码带入不属于该主体的候选路径，因此不采用。

### 2. 查询范围未就绪时显式不可用，不自动借用或刷新

`search(query, permissions=...)` 在当前范围没有成功索引时返回 `INDEX_UNAVAILABLE`。调用方在请求边界先用同一范围执行就绪检查与 `refresh`；查询方法本身不隐式访问目录或 Embedding，以保持故障位置可解释。

替代方案是复用最近一次索引或在查询中自动刷新。前者会违反权限边界，后者会隐藏 Embedding/目录故障并把读操作变成不可预测的网络操作，因此不采用。

### 3. 索引失败只保留同一权限范围的旧结果

某个范围重建失败时，该范围此前成功的索引保持可用；没有旧索引的范围仍为不可用。不同权限范围的索引永不作为故障回退来源。

### 4. 调用链只传递权限，不扩大职责

候选服务及现有意图识别调用方只传递已解析的权限集合。候选返回值继续只包含能力代码、相似度和检索元数据；调用方仍需在后续阶段重新从目录读取并校验条目，候选结果不能成为授权依据。

## Risks / Trade-offs

- [权限范围组合过多导致进程内索引增长] -> 首版目录规模较小且索引仅保存能力向量；若权限模型演化为高基数主体权限，在独立 change 中加入有界缓存或外部缓存，不在本 change 预设 Redis。
- [目录或 Embedding 临时失败] -> 当前范围返回显式不可用；已有同范围索引保持，绝不切换到其他范围。
- [旧调用方未传递权限] -> 空权限仍是一个明确的公共范围；更新所有生产调用点和测试，保证有权限的请求不会隐式落入公共范围。

## Migration Plan

无数据迁移。部署时替换进程内服务实现；重启后每个权限范围在首次请求边界刷新。回滚只恢复单索引实现和调用签名，不影响目录数据、Conversation 或既有 HTTP 路由。

## Open Questions

无。是否采用有界缓存取决于后续权限模型规模，暂不提前引入缓存中间件。
