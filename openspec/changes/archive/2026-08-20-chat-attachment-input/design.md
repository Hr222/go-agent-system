## Context

聊天页目前显示回形针图标，但它没有点击处理或文件输入。通用 `AttachmentPicker` 已经封装了受控上传和失败状态，然而未被聊天页使用；对话流客户端则固定发送空的 `provided_inputs`。后端已经接受 `provided_inputs.source_document`，并在能力识别后以服务端主体、能力声明和显式确认约束附件。

## Goals / Non-Goals

**Goals:**

- 让用户可从聊天页选择、上传、重试和移除一个附件。
- 仅在上传成功后把不透明 `attachment_id` 传入现有对话流请求。
- 使当前 Tender 招标文件场景能走到既有的识别和确认门禁。
- 维持纯文本聊天的请求体和交互结果。

**Non-Goals:**

- 不修改上传、对话流、权限或 Tender 的 HTTP 契约。
- 不在浏览器端识别能力、解析附件或直接调用 Agent。
- 不支持同一对话请求附带多个字段映射或多个附件；后续能力的动态映射另建 Change。
- 不实现附件下载、长期会话列表或工作流编排。

## Decisions

### 直接在聊天编辑器中组合 `AttachmentPicker`

聊天页持有一个 `AttachmentRef[]`，并以 `maxCount=1` 组合现有组件，取代无行为的回形针按钮。这样复用进度、重试和移除逻辑，也避免新增第二套上传状态机。选择单个附件与当前 `source_document` 契约匹配；保留多附件 UI 而丢弃额外引用会造成用户无法预期的结果。

备选方案是在聊天页复制一个隐藏 `<input type="file">` 和上传逻辑。该方案会绕开已有的错误处理与安全引用边界，因此不采用。

### 将已上传引用显式传递给流客户端

流客户端和 Hook 在既有 `conversationId` 参数之后新增可选 `providedInputs` 参数，默认空对象。聊天页只构造 `{ source_document: attachmentId }`，不传文件对象或完整上传响应。保留默认值可使无附件调用继续生成与现在相同的请求体。

备选方案是让 `AttachmentPicker` 知道业务字段并直接发送聊天请求。该方案会把通用组件绑定到 Tender，破坏复用边界，因此不采用。

### 上传状态纳入编辑器忙碌状态

聊天页从组件状态判断是否存在未完成上传。上传中禁止发送，避免将不存在或失败的附件引用传到服务端；上传失败时允许重试和移除。已上传附件仍可随普通文本发送，服务端决定它是澄清、拒绝还是进入确认提议。

## Risks / Trade-offs

- [新会话上传时尚无会话 ID] → 使用现有的主体绑定上传；服务端在后续对话中仍按主体和能力约束读取附件。
- [用户上传非 Tender 支持的格式] → 上传层可接受通用类型；当请求被识别为 Tender 时，服务端按能力声明拒绝不符合的媒体类型，浏览器不自行绕过规则。
- [上传后未发送而暂存文件保留] → 沿用现有附件保留期和过期清理，不新增浏览器端持久化。

## Migration Plan

前端发布后即可生效，无数据迁移。若需回滚，恢复聊天页原有无附件编辑器和流客户端默认空输入；已暂存附件按现有保留策略自然过期。

## Open Questions

无。当前仅映射一个 `source_document`；后续多能力、多附件字段映射需依据能力目录另行设计。
