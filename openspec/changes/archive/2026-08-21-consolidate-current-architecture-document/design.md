## Context

当前架构曾被拆分为四份入口文档：`ARCHITECTURE.md` 只提供索引，`ARCHITECTURE_V1.md` 描述平台基线，`ARCHITECTURE_V2.md` 描述对话体系演化，`FRONTEND_ARCHITECTURE.md` 描述前端工程边界。统一文档已经吸收其内容；继续保留并维护这些副本会增加实施决策和文档同步成本。

本 Change 只改变架构文档的组织和权威关系。运行时代码、数据库与 API 保持不变。当前 `evolve-v2-conversation-memory-boundary` 仍是独立的未实施设计，它不得因本文档合并而被当作已实现能力。

## Goals / Non-Goals

**Goals:**

- 建立一份覆盖后端、对话运行时与前端工程的当前架构基线。
- 在同一份文档内明确分层职责、依赖方向、运行时边界、请求流程、目录结构和演化边界。
- 让后续 Change 只需读取 `ARCHITECTURE.md` 即可获得当前架构约束。
- 删除已被统一基线吸收的旧架构文档，并消除当前维护文档中的引用。

**Non-Goals:**

- 不重构应用模块、目录、接口或数据库。
- 不实现 `owner_subject`、真实认证、Redis、MongoDB、上下文压缩、SubAgent、Workflow、Task Management 或 Harness。
- 不把尚未落地的对话设计改写成已实现事实。
- 不修改已归档 Change 的内容。

## Decisions

### 1. `ARCHITECTURE.md` 是唯一权威入口

统一文档按“事实与边界”组织，不按 V1/V2 版本组织。它同时包含平台分层、LLM 对话运行时、主体与会话隔离目标、附件与知识库、前端工程分层和代码目录。

选择单一入口，是因为当前没有需要对外承诺的版本兼容面。保留 V1/V2 双基线的替代方案会继续要求开发者判断两个文档的优先级，不能解决当前问题。

### 2. 计划能力必须有显式状态

统一文档将“当前已实现”“已确认但未实现”“明确不在当前范围”分开表达。尤其是 `PrincipalResolverPort`、会话 owner 隔离、缓存、上下文压缩和多 Agent 编排，必须保持为边界或后续演化项，不能写成运行时事实。

选择显式状态而不是删除目标设计，是为了保留已确认的依赖方向和插口，减少后续 Change 的重复探索。

### 3. 前端细则并入同一基线

`FRONTEND_ARCHITECTURE.md` 的分层、请求规范、状态管理、页面边界、类型约束和验证规则进入统一文档的前端章节。统一文档保留前后端边界，避免将 React 组件内部设计误写为后端职责。

选择完整并入而不是仅链接，是为了满足“一份当前架构文档”的要求；统一文档增加从后端到前端的目录以保持可读性。

### 4. 删除已合并的旧架构文档

`ARCHITECTURE_V1.md`、`ARCHITECTURE_V2.md` 和 `FRONTEND_ARCHITECTURE.md` 已完整合并到 `ARCHITECTURE.md` 后删除。`agent.md`、OpenSpec 配置、OpenSpec 使用约定和当前阶段看板只引用 `ARCHITECTURE.md`。

Git 历史保留旧文档的审计能力；删除工作树文件可避免后续产生第二份维护源。已归档 Change 的历史文本不修改。

## Risks / Trade-offs

- [统一文档过长，查找成本上升] → 使用稳定目录、模块边界表和分层章节；历史细节不在正文重复两次。
- [计划被误认为已实现] → 每个相关章节标明实现状态，并把验收事实继续交给归档 Change。
- [删除后出现当前引用断链] → 删除前搜索并更新当前维护文档、OpenSpec 配置和未归档 Change 中的引用；归档 Change 保持历史原样。
- [合并时遗漏原有约束] → 按来源文档建立迁移清单，逐项复核后再运行文档与 OpenSpec 校验。
