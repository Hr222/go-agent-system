## Context

附件是服务端管理的临时资源，现有实现会把它绑定到 `RequestPrincipal.subject` 和可选会话。但匿名 resolver 返回空主体，上传路径仍允许写入，后续读取和消费却因无法验证归属而统一返回不可用。`.env.example` 还将该不可用模式作为启动示例。

## Goals / Non-Goals

**Goals:**

- 让附件创建、读取、消费和删除共享“必须具备可信主体”的资源归属前提。
- 让 HTTP 调用方在上传时就得到稳定且可诊断的拒绝结果。
- 提供能完成附件闭环的受控本地开发主体示例。

**Non-Goals:**

- 不把匿名请求归并到固定主体，不引入浏览器指纹、客户端自报 ID 或共享匿名资源域。
- 不实现 JWT、Session、SSO、真实用户、Conversation owner 隔离或会话访问控制。
- 不改变附件的随机 ID、会话绑定、TTL、一次性消费或文件校验策略。

## Decisions

### 在 Attachment 契约处要求非空主体

`AttachmentAccessContext` 是附件存储和 Interaction 附件解析之间的稳定内部契约。将 `subject` 设为必填的非空文本，防止任何适配器绕过 HTTP 路由直接暂存无归属文件。文件系统存储无需为匿名记录建立特殊状态。

仅在 HTTP 路由检查主体不可保证其他未来入口遵守规则；允许空主体再以附件 ID 的随机性保护访问也会继续产生无法合法消费的引用，因此不采用。

### 在 HTTP 边界显式拒绝匿名上传

上传路由在构造 `AttachmentAccessContext` 前检查解析后的主体。主体缺失时返回 `403` 和固定错误码 `ATTACHMENT_PRINCIPAL_REQUIRED`，不调用存储端口。输入格式、媒体类型和大小错误继续走既有 `400 INVALID_INPUT` 映射。

不使用 `401`，因为当前匿名模式是一个已被成功解析的运行配置，而不是 HTTP 凭据校验失败；调用方需要的是具备资源归属的受控主体。

### 示例环境显式使用静态开发主体

`.env.example` 提供非空 `STATIC_PRINCIPAL_SUBJECT` 和 Tender 权限，并将模式设为 `static`。这只是一台受控本地开发服务的服务端 Mock 身份；真实部署必须配置认证适配器和真实主体来源。`Settings` 代码默认值仍为 `anonymous`，以保持没有配置时的零权限安全语义和既有主体模式契约。

## Risks / Trade-offs

- [复制示例配置到多人或公网环境会使请求共享开发主体] → 在示例旁明确限定受控本地开发；真实部署接入认证适配器。
- [匿名模式中的附件操作由成功改为拒绝] → 这是有意的契约修复；错误码引导调用方配置静态主体或认证。
- [未来的协议适配器直接创建附件] → Attachment 契约会在端口层拒绝无主体上下文，促使该适配器显式解析可信身份。

## Migration Plan

1. 部署前为使用附件的环境配置非空、可信的主体 resolver；本地可采用示例中的静态 Mock。
2. 匿名调用上传接口将收到 `403 ATTACHMENT_PRINCIPAL_REQUIRED`，不产生需清理的附件。
3. 回滚只需恢复之前版本；不会涉及持久化数据或文件格式迁移。
