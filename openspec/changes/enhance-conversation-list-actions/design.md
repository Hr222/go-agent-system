## Context

当前 Conversation 已有主体隔离的摘要列表、历史读取和话题概括更新能力，但摘要只支持点击切换。目标交互将会话管理入口放到每个列表项的更多菜单中，同时引入置顶和删除这两类需要持久化及权限校验的行为。变更跨越 Conversation 领域、HTTP、PostgreSQL 和 Chat 前端，因此需要先固定端口与数据契约。

## Goals / Non-Goals

**Goals:**

- 在当前主体范围内提供重命名、删除和置顶，并展示分享占位项。
- 让置顶状态参与服务端排序和稳定分页。
- 让删除在服务端执行主体校验，并依靠既有外键级联删除消息和事件。
- 让前端菜单、确认、处理中、成功和失败状态可观察，并保持 React Query 列表缓存一致。

**Non-Goals:**

- 不引入分享服务、短链服务、剪贴板复制或公开访问权限；分享只作为无动作占位项。
- 不恢复或猜测历史会话的话题概括；已有 `NULL` 仍然保持 `NULL`。
- 不实现跨主体分享、回收站、多选、批量 HTTP 接口或永久软删除。
- 不改变消息历史、流式对话和 Agent 调用的业务语义。

## Decisions

### 1. 以 Conversation 为唯一管理边界

新增置顶字段 `is_pinned`，默认 `false`，并在 `ConversationSummary`、HTTP 摘要和列表 API 中返回。列表排序使用 `is_pinned DESC, updated_at DESC, id DESC`；游标同时携带置顶状态，避免置顶分组变化造成重复或漏项。旧的两字段游标在读取时按未置顶兼容解析。

备选方案是只在前端排序，但会导致分页顺序不一致且不同客户端看到的结果不同，因此不采用。

### 2. 通过主体范围应用服务执行管理写操作

在 Conversation 应用层增加管理服务和写端口操作：切换置顶状态、删除会话。HTTP 路由只负责解析请求主体、映射 404/422 和返回安全摘要；应用服务先用 `ConversationAccessService.resolve` 校验主体，再调用写端口。具体 SQLAlchemy 实现继续放在 infrastructure，由 composition root 组装。

删除使用真实删除，依赖 `conversation_message`、`conversation_event` 已有的 `ON DELETE CASCADE`。这与当前会话事实模型一致，也避免为本次列表管理引入回收站状态。

### 3. 前端菜单状态局部化

每个会话项使用菜单按钮阻止冒泡，菜单动作按“重命名、删除、置顶、分享占位”提供。重命名复用既有话题概括 PATCH；删除和置顶调用主体范围接口；分享按钮不执行任何操作。每次真实操作成功后失效会话列表缓存并显示结果反馈。

分享占位项明确不产生网络请求、剪贴板写入或会话状态变化。

### 4. 破坏性操作必须二次确认

单项删除使用原生确认对话框或等价的确认状态，确认前不发请求。删除当前会话后清理 active conversation、历史缓存和编辑草稿；删除其他会话后只刷新列表。置顶、重命名和分享占位项不需要确认。

## Risks / Trade-offs

- [删除不可恢复] -> 仅允许主体范围删除，前端强制二次确认，并在测试中覆盖错误主体和级联事实。
- [置顶状态改变游标顺序] -> 游标携带 `is_pinned`，并保留旧游标兼容解析。
- [分享尚未实现] -> 保留可见的无动作占位项，避免伪造复制成功或引入未定义的访问权限。
- [列表菜单遮挡或超出侧栏] -> 菜单使用相对定位和最高层级，列表仍保持独立滚动，移动窄屏时折叠为全宽操作区。

## Migration Plan

1. 执行幂等 SQL 迁移，新增 `conversation.is_pinned BOOLEAN NOT NULL DEFAULT FALSE` 及索引，历史记录全部默认未置顶。
2. 部署后端读写契约和前端菜单；旧客户端忽略新增字段即可继续读取列表。
3. 若需回滚代码，可保留新增列和索引；旧代码仍可读写 `topic_summary`，不依赖 `is_pinned`。
4. 不执行数据删除迁移；用户确认删除后由应用实时删除级联事实。

## Open Questions

无。分享当前仅作为无动作占位项，不改变 Conversation 的访问权限。
