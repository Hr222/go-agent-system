## Requirements
### Requirement: 系统对招标 DOCX 建立可追溯的有限分块

系统 MUST 在 50MB 以内的招标 DOCX 进入 LLM 分析前，按标题路径、段落顺序、表格边界和证据标识建立有限大小的分块；系统不得因为文件字节数在上限内就把整份文档作为一次 LLM 输入。

#### Scenario: 中等大小文件也必须分块

- **WHEN** 用户提交一个文件大小不超过 50MB、但解析文本超过单次模型预算的 DOCX
- **THEN** 系统将其拆成两个或多个带 `chunk_id` 和 `evidence_id` 列表的分块
- **AND** 每个分块的输入规模不超过当前 Provider 配置的单次预算
- **AND** 分块之间保留章节路径和源文档顺序

#### Scenario: 表格和章节边界被保留

- **WHEN** DOCX 包含标题层级、表格或附件模板
- **THEN** 系统不会在表格中间或无法解释的章节边界处静默截断
- **AND** 超预算表格按行组拆分时保留表头和原始证据引用

### Requirement: 分块分析只提取有证据的局部要求

系统 MUST 对每个分块输出紧凑的局部分析结果，包含明确要求、投标文件或分册候选、章节/表格/函件/附件、提交规则、证据引用和待确认项；分块结果 MUST 不得编造公司事实，也不得仅凭局部内容最终决定整体单卷/多卷。

#### Scenario: 分块结果包含源文档依据

- **WHEN** 分块中出现投标组成、提交要求或模板内容
- **THEN** 局部结果中的每个相关结论都引用该分块可用的 `evidence_id`
- **AND** 局部结果不引用公司知识库、历史投标书或行业惯例

#### Scenario: 分块证据不足

- **WHEN** 一个分块无法判断要求属于哪份投标文件，或文本只出现标题没有正文
- **THEN** 局部结果标记待确认项和可用证据
- **AND** 系统不静默补充分册、章节或公司内容

### Requirement: 系统通过全局归并生成统一 TenderAnalysis

系统 MUST 对分块结果执行一个或多个有界的全局归并阶段，去重并处理跨块冲突，最终生成与现有 `TenderAnalysis` 契约一致的结果；单卷/多卷、输出数量、服务交付成果区分和最终分线 MUST 在全局归并阶段确定。

#### Scenario: 多个分块组成单卷结果

- **WHEN** 多个分块分别出现技术要求、商务要求和报价要求，但源文件明确要求一份投标文件
- **THEN** 全局结果将这些要求归入同一个输出文件
- **AND** 输出文件数量、章节归属和证据引用与归并结果一致

#### Scenario: 多个分块组成多卷结果

- **WHEN** 不同分块明确要求技术标、商务标或报价文件分别编制、封装或提交
- **THEN** 全局结果为每个明确分线生成独立输出项
- **AND** 系统不会把局部结果简单拼接成未经源文件要求确认的合订本

#### Scenario: 跨分块要求存在冲突

- **WHEN** 不同分块对分线、递交方式或文件组成给出无法消除的冲突
- **THEN** 全局结果标记待确认项并保留冲突双方的源文档依据
- **AND** 系统不得静默选择一个结论并生成已完成状态

### Requirement: 分块和归并过程受调用预算约束

系统 MUST 对单块调用、归并批次和整个请求分别执行输入规模、输出规模、超时、重试次数和总调用数量控制；Provider 失败、超时或契约错误 MUST 转换为稳定的业务失败或待确认结果。

#### Scenario: 单个分块调用超时

- **WHEN** 一个分块的 Provider 调用达到配置的超时时间
- **THEN** 系统只执行有限重试并记录阶段、chunk_id、Prompt 版本、异常类型和耗时
- **AND** 系统不记录原始招标文本、用户关注点、API Key 或 Provider 原文到用户响应

#### Scenario: 分块失败导致覆盖性无法确认

- **WHEN** 一个或多个关键分块在有限重试后仍失败
- **THEN** 系统返回稳定的分析失败或待确认结果，并标明失败批次
- **AND** 系统不生成声称已完整覆盖招标要求的骨架文件

#### Scenario: 归并结果过大

- **WHEN** 分块结果数量超过单次归并预算
- **THEN** 系统按有界批次继续归并
- **AND** 每个归并结果保留下属证据引用，最终阶段不接收无界的全部原文

### Requirement: 系统执行文件大小和解压资源限制

系统 MUST 将 50MB 以内 DOCX 作为正常分析范围，并设置 70MB 的服务端绝对拒绝线；系统 MUST 在解压和解析阶段限制解压总量、文件条目和异常压缩比，避免上传大小检查被压缩容器绕过。

#### Scenario: 正常范围内的 DOCX

- **WHEN** 用户提交非空、格式正确且不超过 50MB 的 DOCX
- **THEN** 系统继续执行请求级解析、分块分析和全局归并
- **AND** 系统不把原始文件写入持久化知识库或长期任务存储

#### Scenario: 超过绝对大小线的 DOCX

- **WHEN** 用户提交超过 70MB 的 DOCX
- **THEN** HTTP 返回稳定的文件大小错误，MCP 返回稳定的工具输入错误
- **AND** 系统不执行 DOCX 解析、LLM 调用或骨架渲染

### Requirement: 分块流程保持现有调用契约和资源清理边界

系统 MUST 继续通过现有 HTTP 和 MCP 入口将一次请求转换为一个 Tender Application Command；分块过程不得创建 `task_id`、会话历史或持久索引，且成功、失败和客户端中断时都必须清理请求级临时资源。

#### Scenario: 分块流程成功

- **WHEN** 所有必要分块完成、全局归并通过 Schema 校验且来源证据有效
- **THEN** HTTP 和 MCP 返回与现有 V1 一致的分析结果和一个或多个 DOCX 骨架
- **AND** 输出数量、名称、分线和证据引用与全局结果一致

#### Scenario: 客户端在分块期间中断

- **WHEN** HTTP 或 MCP 客户端在某个分块或归并阶段中断请求
- **THEN** 系统终止或回收本次请求的剩余工作
- **AND** 系统清理临时文件和中间结果，不创建持久任务记录
